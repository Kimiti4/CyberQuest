## 1. Executive decision

CYBERQUEST is a security-sensitive learning platform. It stores account identifiers, learner profiles, learning activity, assessment answers and security-relevant audit events. Its trust model must protect both learner data and the integrity of learning outcomes.

The design baseline is:

1. Treat every client, offline queue, request body, content import and AI-generated suggestion as untrusted.
2. Authenticate at the API boundary and authorize every resource operation against the authenticated actor and intended role.
3. Keep completion, scoring, XP, achievements, competencies and entitlements server-authoritative.
4. Minimize personal data and avoid collecting device telemetry unrelated to a documented purpose.
5. Keep MVP exercises fictional, deterministic and non-executable.
6. Defer executable labs until isolation, egress denial, quotas, credential isolation, expiry, teardown and audit controls are independently demonstrated.
7. Fail closed when identity, authorization, integrity or lab-safety evidence is missing.

**No production security control is certified by this threat model.** The current repository contains a small health API and identity mapping schema, not a complete identity, authorization, learner or production system.

### 2.2 Data-flow overview

`Learner → Android/Web → HTTPS API → domain services → PostgreSQL`

Content authors/reviewers submit declarative content through a future controlled publication path. CI builds software from repository content and dependencies. A future identity provider authenticates users; the backend maps provider subjects to internal user IDs.

Offline clients may cache approved content and queue interaction events. On reconnection, the server authenticates the actor, validates the event against the immutable attempt/content version, applies idempotency and determines the outcome. The client cannot mint authoritative results.

There is no production deployment, external identity integration, telemetry vendor, payment provider or executable lab plane in the assessed baseline.

| Asset | Required property | Failure impact |
|---|---|---|
| Account and recovery identity | Confidentiality, integrity, availability | Account takeover, learner lockout or impersonation |
| Learner profile and activity | Confidentiality, purpose limitation, integrity | Privacy harm, profiling, discrimination or exposure |
| Assessment responses and evidence | Confidentiality, integrity, correct attribution | Answer leakage, false mastery or unfair outcomes |

| Mission/content versions | Integrity, authenticity, safety | Malicious instruction, altered scoring or unsafe learning |

| Administrative controls | Least privilege and accountability | Bulk exposure, content poisoning or privilege abuse |

| Build/release artefacts | Provenance and integrity | Supply-chain compromise |
| Future lab isolation boundary | Containment and resource control | Host compromise, public targeting or financial abuse |

Security objectives: confidentiality, integrity, availability, authenticity, authorization, accountability, privacy, learner safety and correctness of competency evidence.

## 4. Actors and trust boundaries

### Actors
- Anonymous visitor: can access only deliberately public marketing and health/liveness surfaces.
- Authenticated learner: can access only their own profile, attempts, answers and progress plus published content.
- Parent/guardian: no access is assumed; any future role requires explicit verified relationship, narrow scope and lawful basis.
- Content author/reviewer: proposes and approves content under separated permissions; no direct production database access.
- Support operator: narrowly scoped support access; no default access to answer content or tokens.
- Administrator: MFA, least privilege, audited actions and time-bounded elevated access.
- CI runner/dependency publisher: external build inputs; no production credentials in ordinary CI.
- External identity/hosting/analytics providers: processors or independent controllers depending on actual contracts and purposes; role must be assessed, not assumed.

### Boundaries
1. Public internet ↔ web/Android clients.
2. Client ↔ API: all payloads and client state are untrusted.
3. API ↔ identity provider: token issuer, audience, signature, expiry, nonce/state and key-rotation validation.
4. API ↔ PostgreSQL: least-privilege service identity, parameterized queries, migrations separated from runtime.
5. Content authoring ↔ publication: review, schema validation, immutable version and rollback.
6. CI ↔ repository/dependency ecosystem: pinned actions, lockfiles, minimal permissions and artifact provenance.
7. Future lab control plane ↔ execution workload/network: separate security domain; never trust learner-controlled workload policy.

## 5. Threat analysis method

Use STRIDE to identify threat classes and assess likelihood/impact qualitatively. Priority is not a claim of exploitability. Severity is elevated where a plausible threat exposes multiple learners, compromises authoritative learning records, or crosses into real-world systems.

- **Critical:** credible path to broad sensitive-data exposure, systemic account compromise, unauthorized real-world targeting or control-plane escape.
- **High:** material account/data compromise, privilege escalation, reward/competency corruption or sustained service disruption.
- **Medium:** bounded misuse or privacy/integrity issue with constrained impact.
- **Low:** limited impact with effective containment.

Likelihood and residual risk must be reassessed after implementation and independent testing. Planned controls are not implemented controls.

|---|---|---|---|---|

## 7. Privacy data inventory and minimization

The inventory below is a proposed minimum. It must be validated against the actual product, vendors and lawful purposes before collection.

| Data category | Proposed MVP fields | Purpose | Classification | Default decision |
|---|---|---|---|---|
| Account identity | Username and email; internal UUID; provider subject only after provider selection | Create and recover an account | Personal data / identifier | Username and email are the only planned required account fields; real identity integration deferred; synthetic identities for demo |
| Optional profile | Display name and learner preferences | Personalize learning display | Personal data | Declined by default; collect only after explicit user choice |
| Learning activity | Mission/version IDs, attempt state, completion timestamps, progress | Resume learning and assess competence | Personal/behavioural | Optional persistence; user authorizes saving and chooses an available retention period; declining means no server-side learning-history retention |
| Assessment | Answers, evidence, scoring result and rubric version | Evaluate learning | Personal/educational profile | Persist only when the user authorizes saved progress; restrict access; do not expose answer keys |
| Security/audit | Actor ID, action, target ID, timestamp, request ID, outcome | Security/accountability | Potentially personal | No tokens/passwords/full answer payloads; restricted access |
| Support/feedback | User-entered feedback and optional contact channel | Resolve issues | May contain sensitive free text | Warn users not to submit secrets; redact and expire |
| Device/cache | Minimal app state and content cache | Offline learning | Device-linked data | No contacts/SMS/call logs/location/installed-app inventory |
| Diagnostics | Coarse error code, app version, request ID | Reliability | May become personal when linkable | Optional; no advertising ID or raw request body; explicit choice and retention control required before collection |
| Payments (deferred) | Provider transaction reference and entitlement result | Subscription fulfilment | Financially sensitive context | Do not store card/mobile-money credentials; provider-hosted flow |
| Lab telemetry (deferred) | Lab/session ID, resource usage, safety events | Containment and audit | Potentially personal/security sensitive | Separate design and DPIA/security review before any lab launch |

**Prohibited by default for MVP:** national ID number, precise location, contacts, SMS, call logs, photos, microphone, camera, installed-app inventory, browsing history, advertising ID, biometric data, health data, payment credentials and raw device file contents.

Free-text fields create unpredictable collection risk. Provide prompts not to include passwords, one-time codes, financial details, personal data of third parties or real target information. Apply access controls, redaction and retention to submitted text.

### Retention and deletion

The product direction is to retain only username and email as required account data. Other personal or learning data must be declined by default or collected only after a clear user choice; where persistence is enabled, the user should select a disclosed retention period. A user choice cannot override a narrowly applicable legal/security retention obligation. Before public beta, engineering must implement deletion/expiry and backup propagation, and the founder must approve a documented schedule for unavoidable security, operational and legal records after qualified review. The synthetic demo must not use real learner data.

## 8. Kenya privacy and data-governance workstream (production-readiness gate)

This is a requirements register, not a legal opinion or compliance determination.

- Review Kenya Data Protection Act, 2019, including data protection principles, data-subject rights, collection notices, lawful processing, DPIA, consent and child-data provisions.
- Review the Data Protection (General) Regulations, 2021 and Registration of Data Controllers and Data Processors Regulations, 2021.
- Obtain qualified Kenyan privacy counsel's advice on controller/processor role, ODPC registration applicability, lawful bases per purpose, notices, cross-border transfers, retention, breach response and contracts.
- The initial release is adults-only (18+); child accounts and child-directed processing are out of scope. Any future expansion to minors requires separate founder approval, revised threat modelling and qualified legal/safeguarding review before implementation.
- A DPIA must be assessed before high-risk processing; the statutory and ODPC guidance requirements must be reviewed by counsel before such processing.
- Do not assume consent is the correct lawful basis for every operation. Record purpose-by-purpose legal-basis analysis.
- Implement and test a proportionate 18+ age gate before live learner registration. Do not collect full date of birth by default; select an age-assurance method during production-readiness review.
- Assess ODPC registration requirements against the actual entity, purposes and processing activities before collecting live learner data.

## 9. Security control requirements before identity implementation

CQ-01 must not begin implementation of authentication or learner endpoints until the following designs are resolved:

1. Identity provider decision, data processing role, token/session model and account recovery threat model.
2. Token validation contract: allowed issuer/audience/algorithms, key rotation, expiry, revocation and failure behavior.
3. Authorization model for learner, reviewer, support and administrator roles; object-level authorization policy.
4. Account lifecycle: signup, verification, recovery, logout, account deletion, account linking and duplicate identity handling.
5. Session storage: web cookie strategy or documented alternative; Android secure storage; refresh/revocation behavior.
6. Abuse controls: rate limits, credential stuffing, enumeration resistance, recovery throttling and security alerts.
7. Privacy notice, lawful basis, retention and data-subject request process for each data category.
8. Audit event schema, access controls and redaction.
9. Adversarial test matrix: two-user isolation, horizontal/vertical privilege escalation, token invalidation, replay, race/duplicate submissions and account-switch offline queue.
10. Dependency, secret, static-analysis and release verification plan.

Controls must be implemented and tested; a written design does not close the gate.

## 10. Cyber-safety content and future lab controls

### MVP content publication gate

- Fictional brands, users, domains, IP addresses and credentials only.
- No live credential collection, credential replay, malware, exploit payloads, persistence, evasion or uncontrolled scanning instructions.
- No arbitrary HTML/script, executable mission files or arbitrary external URLs.
- Validate mission schema and content length/types; render text safely.
- Independent content/safety review before publication; version and retain reviewer evidence.
- Every simulation clearly states what is simulated and what is not detected or protected in the real world.
- A report/remove path for unsafe or inaccurate content.

### Future technical labs

A future lab launch is blocked until all are independently verified: separate control plane; approved immutable image digest; no privileged mode or host socket/mount; default-deny network egress; block public targets unless explicitly allowlisted and authorized; block private, loopback, link-local and cloud metadata destinations; policy enforced outside learner control; per-user/session CPU, memory, disk, process and time quotas; isolated short-lived credentials; session expiry and verified teardown; tamper-resistant audit; abuse detection; emergency stop; restore/rebuild procedure; independent escape and network-policy tests. No lab is approved by this document.
