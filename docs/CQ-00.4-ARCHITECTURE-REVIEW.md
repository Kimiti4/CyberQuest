# CQ-00.4 — Cross-Platform Architecture and Toolchain Readiness

**Checkpoint:** CQ-00.4  
**Classification:** DESIGN ONLY / PARTIAL  
**Baseline:** CQ-00.3 candidate `fdefbe5350f96d01b3a0695ea84d785fd40e0933`

## Executive decision

Retain native Android (Kotlin/Compose), companion web (Next.js/TypeScript), Python/FastAPI modular monolith and PostgreSQL. The architecture is viable for MVP if clients remain presentation/offline-cache layers and the backend owns authoritative learning, security and commercial decisions. The four pillars are product experiences over shared platform capabilities, not four independent apps or services.

This review does not certify a working Android build, Next.js build, deployed API, production identity integration or cyber range.

## Four-pillar coverage

| Pillar | Initial delivery | Shared capabilities | Deferred capability |
|---|---|---|---|
| Cyber Academy | Lessons, content versions, knowledge checks | Curriculum, assessment, competency evidence, progress | Institutional authoring |
| Cyber Defense | Deterministic fictional incident scenarios | Mission runtime, evidence, assessment, audit | Real telemetry and endpoint monitoring |
| Cyber Labs | Static and simulated exercises only | Mission catalogue and safety policy metadata | Executable isolated labs pending independent isolation proof |
| Cyber Arena | Not in MVP | Shared identity, content and scoring boundaries | CTF hosting, teams, rankings and anti-cheat |

Do not duplicate accounts, XP ledgers, content versions or competency records across pillars.

## Module ownership

| Module | Owns | Boundary |
|---|---|---|
| Identity integration | Provider subject mapping, account lifecycle, token validation boundary | No XP or competency authority |
| Learner profile | Preferences and profile lifecycle | No authentication secrets |
| Curriculum/content | Courses, modules, lessons, immutable versions, publication | No assessment outcomes |
| Mission catalogue/runtime | Declarative missions, versions, attempts, stage state | No arbitrary code execution or direct reward minting |
| Assessment | Question sets, deterministic scoring, attempts and evidence | No client-trusted scores |
| Competency | Definitions, criteria, evidence links, mastery state | XP alone is insufficient |
| Progress/rewards | Append-only XP ledger, achievements, idempotency | Backend-only award decisions |
| Digital protection | Educational guidance and user-selected checklists | No antivirus/device-scanning claims |
| Lab governance (future) | Templates, policy approvals, session lifecycle and audit | Learner cannot control isolation |
| Arena (future) | Competition definitions, submissions and anti-cheat evidence | No duplicate identity or assessment authority |
| Entitlements | Plans, grants and access decisions | Never trust unverified payment callbacks |
| Analytics/reporting | Minimized derived metrics | Not a source of truth |
| Administration/audit | Moderation and privileged-action audit | No silent mutation of learning evidence |

Modules share one PostgreSQL database initially, but cross-module writes go through explicit service interfaces. Avoid circular imports and direct cross-module table mutation.

## Authority and data flow

1. Clients authenticate and call one versioned HTTPS API.
2. API middleware validates identity proof and resolves a local account.
3. Domain services authorize every operation; hiding UI controls is not authorization.
4. Content and missions carry immutable version identifiers.
5. Clients submit attempt events and evidence references, not authoritative scores or rewards.
6. Backend validates attempts against pinned versions and applies deterministic assessment rules transactionally.
7. XP ledger writes use idempotency keys and database uniqueness/transaction constraints.
8. Competency mastery requires explicit evidence criteria.
9. Analytics consume minimized derived events and cannot mutate source-of-truth records.

Client-supplied XP, mastery, entitlement or assessment results are never authoritative.

## Offline synchronization contract

Offline mode is approved-content cache plus queued event submission. It is not a second authority.

- Each event carries a client event UUID, schema version, content/mission version, event type and payload.
- The authenticated server establishes actor identity and receipt time.
- Server validates schema, ownership, content version, allowed transition, idempotency/replay and assessment rules.
- Duplicate event IDs return the original result and never award twice.
- Stale or revoked content is rejected or explicitly remediated; never silently assessed against a newer version.
- Client timestamps are advisory, not proof or authoritative ordering.
- Outcomes are explicit: accepted, duplicate, stale-version, invalid-transition, unauthorized or retryable.
- Logout/account switch clears or cryptographically separates queued user data.
- Credentials use platform-appropriate secure storage; personal data in cache is minimized.

Offline actions may remain pending or be rejected after synchronization. This is preferable to granting unverifiable rewards.

## API and client contract

- One versioned HTTPS REST API; OpenAPI is the contract artifact, not proof of endpoint implementation.
- Route handlers validate transport input and delegate domain work to services.
- Explicit Pydantic request/response schemas; reject malformed or unknown fields where appropriate.
- Contract-checked or generated clients where practical; avoid divergent copies of enums and schemas.
- Breaking changes require explicit version/deprecation decisions and client compatibility tests.
- Stable error envelope: machine-readable code, safe message, request ID and retryability; never expose stack traces or secrets.
- Define pagination, rate limits, idempotency and authorization per operation.

## Authentication and authorization direction

Identity implementation is blocked pending a dedicated provider/session threat model and ADR.

- Keep provider-specific OIDC integration behind an adapter.
- Validate issuer, audience, signature, expiry and relevant nonce/state/PKCE protections.
- Android candidate: Authorization Code with PKCE.
- Web candidate: reviewed BFF/server-session or PKCE approach; choose after cookie, CSRF and deployment analysis.
- Authorization is server-side, deny-by-default and resource-aware.
- Admin accounts require MFA and privileged-action auditing.
- Never store provider passwords or long-lived bearer tokens in ordinary preferences or browser local storage.
- Design account linking, recovery, deletion and provider outage behavior before launch.

## Security and safety constraints

- HTTPS only; secure headers and restrictive CORS/CSRF controls appropriate to the selected session model.
- Least-privilege database/service credentials; secrets outside Git and logs.
- Rate limits on authentication, assessment submission, sync and public endpoints.
- Content is declarative, versioned and reviewed; no arbitrary mission scripts or learner-controlled command execution in MVP.
- Executable labs are not enabled. Future launch requires independently verified network isolation, egress denial, metadata/private-network blocking, quotas, credential isolation, expiry, teardown, audit and emergency stop.
- Digital Defense guidance is not real-time device monitoring, antivirus or verified protection.
- Define retention, export, deletion, consent and incident procedures before production.

### Compatibility research checked 2026-11-13

- Next.js 16 is listed as Active LTS; official installation documentation sets Node.js 20.9 as minimum. Node 22 LTS is a candidate; exact patch and npm lockfile must be pinned with the web scaffold. Sources: https://nextjs.org/support-policy and https://nextjs.org/docs/app/getting-started/installation.
- Kotlin Gradle Plugin, Android Gradle Plugin and Gradle must be selected as a compatible tuple, not independently. Sources: https://kotlinlang.org/docs/gradle-configure-project.html, https://developer.android.com/build/releases/about-agp and https://docs.gradle.org/current/userguide/compatibility.html.
- JDK must be selected against the chosen AGP/Gradle tuple. Android documents JDK 17 for AGP 8.x; re-check official tables at scaffold creation.

Do not pin speculative Android or web versions in documentation alone. At scaffold creation, choose a compatible tuple, commit Gradle wrapper and distribution checksum, Gradle dependency verification/locking, exact JDK/Node patches, package-manager lockfile, Android SDK/API and emulator image; then prove clean build, tests and browser/emulator smoke tests in CI.

## Cost and operations

- Keep one backend deployment and managed PostgreSQL candidate for MVP.
- Object storage remains optional until media needs justify it.
- No separate analytics warehouse, cache cluster, queue, service mesh or Kubernetes for MVP.
- Include recurring hosting, database backups, storage, domain, email/identity, observability and distribution costs.
- Verify provider pricing, data residency, export and restore before selecting production provider.
- KES 80K–200K remains the planning constraint. A full professional Android/web/backend team is not affordable within this budget; prioritize one complete learner journey.
