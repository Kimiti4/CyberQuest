## 4. G5 acceptance criteria and test matrix

### 4.1 Gate exit criteria

G5 may be assessed as PASS only when all of the following hold:

1. Every mandatory test below is executed on an eligible reserved device or emulator and has recorded evidence.
2. No open severity-1 (data exposure, privacy breach, crash loop, false success) or severity-2 (core flow blocked, misleading result) defect remains.
3. The five warning indicators and three neutral facts behave correctly on device; false positives reduce the score and are labelled.
4. Server-determined results are rendered without client-side score invention; XP remains 0, competency remains false and persistence remains `not_saved`.
5. Network failure and recovery never produce a false success or an automatic duplicate submission.
6. No account, learner data or persistent progress is found; local cleanup and uninstall remove all app data.
7. The privacy procedure in §6 was followed, with no personal content captured, retained or reused.
8. An independent assessor reviews the evidence and the founder records the G5 decision separately.

### 4.3 Detailed test cases

#### G5-01 — Clean installation and startup

- **Preconditions:** eligible reserved device/emulator; factory-reset or clean test profile; no prior CYBERQUEST install; trusted HTTPS endpoint reachable; APK built from the exact G5 commit.
- **Procedure:** record device identity and APK SHA-256; `adb install -r app-debug.apk`; launch from the launcher; observe startup.
- **Expected:** install succeeds; app opens without crash; the 18+ simulation header, mission title and loading state appear; no login, account or permission prompt beyond internet access (none requested at runtime).
- **Evidence:** install output, launch screenshot, filtered logcat, device/APK metadata.
- **Pass/fail:** PASS if installed and launched with no crash and no account/identity UI. FAIL on crash, blank screen, unexpected permission prompt or personal-data request.
- **Privacy/security:** capture the app window only; do not capture the launcher, notification shade or other apps.

#### G5-02 — Mission content and navigation

- **Preconditions:** G5-01 passed; mission loaded.
- **Procedure:** scroll from top to bottom and back; inspect the briefing, simulated email, all observations and response options; attempt to activate the displayed link.
- **Expected:** all expected content is present and readable; eight observations (five warning signs, three neutral facts) and all response options are reachable; the displayed link is inert; no external browser or navigation is triggered.
- **Evidence:** top/middle/bottom screenshots, UI hierarchy text dump, logcat.
- **Pass/fail:** PASS if all content is reachable, readable and inert. FAIL on missing/truncated core content, external navigation, executable content or unreachable controls.
- **Privacy/security:** synthetic Nexus Corporation content only; no real addresses or targets.

#### G5-03 — Correct assessment and feedback

- **Preconditions:** G5-02 passed; clean app state.
- **Procedure:** select the five warning indicators, leave the three decoys unticked, choose the safe independent-verification response, submit.
- **Expected:** Submit is disabled until a response is selected; one successful POST; result shows 10 / 10; per-indicator guidance for all eight observations; Identified/Neutral fact labels; `XP awarded: 0`; `Competency awarded: false`; `Saved: false`; "not verified competency evidence" message.
- **Evidence:** result screenshot, gateway POST line (status/duration/outcome only), UI text dump.
- **Pass/fail:** PASS if the server result is rendered faithfully with no persistence/XP claim. FAIL on client-invented score, missing guidance, saved/XP claim or duplicate POST.
- **Privacy/security:** only synthetic indicator IDs and a response ID leave the device.

#### G5-04 — Imperfect and false-positive assessment

- **Preconditions:** clean app state; mission loaded.
- **Procedure:** select at least one correct warning sign and at least one neutral decoy; choose a less-safe response; submit.
- **Expected:** server-determined score below maximum; the decoy is labelled False positive; missed warning signs are labelled Missed; neutral facts remain Neutral fact; guidance is shown; no false success.
- **Evidence:** before/after screenshots, gateway POST line, UI text dump.
- **Pass/fail:** PASS if feedback correctly distinguishes identified, missed, false-positive and neutral items and the score reflects the penalty. FAIL on mislabelling or a success claim unsupported by the server result.
- **Privacy/security:** synthetic only.

#### G5-05 — Submit validation and duplicate prevention

- **Preconditions:** mission loaded; no response selected.
- **Procedure:** observe the Submit control before selecting a response; select a response; double-tap Submit rapidly; observe the button and any network activity; after a failure, do not tap again until the error appears.
- **Expected:** Submit disabled with no response; once tapped, it shows `Evaluating…` and is disabled; at most one assessment POST is sent; no automatic retry occurs after failure.
- **Evidence:** screenshots, gateway POST count/timestamps, logcat.
- **Pass/fail:** PASS if duplicate rapid taps do not create duplicate submissions and no retry is automatic. FAIL on duplicate POSTs or auto-retry.
- **Privacy/security:** none beyond synthetic submission.

#### G5-06 — Network loss during mission load

- **Preconditions:** mission previously loaded once; endpoint reachable; device networking controllable.
- **Procedure:** disable Wi-Fi and mobile data (or use airplane mode); from a fresh app start or Retry, attempt to load; restore networking; tap Retry.
- **Expected:** useful error ("Cannot reach the demo API…"), no mission content presented as live, no crash; after restoration, Retry loads the mission.
- **Evidence:** offline/error and recovered screenshots, logcat, API/gateway logs.
- **Pass/fail:** PASS if the error is useful, recovery is explicit and no false success occurs. FAIL on stale content presented as live, silent failure or crash.
- **Privacy/security:** do not open system settings screens containing personal accounts while capturing.

#### G5-07 — Network loss during assessment submission

- **Preconditions:** mission loaded; indicators and response selected; endpoint reachable.
- **Procedure:** disable networking; tap Submit; wait for the error; restore networking; tap Submit again explicitly.
- **Expected:** first submission fails with an error, no result is shown and no automatic retry occurs; the explicit second submission succeeds once and renders the server result; no duplicate assessment is recorded.
- **Evidence:** error and result screenshots, gateway POST count/timestamps, logcat.
- **Pass/fail:** PASS if there is no false success, no auto-retry and exactly one successful POST after explicit recovery. FAIL on invented result, automatic retry or duplicate success.
- **Privacy/security:** none beyond synthetic submission.

#### G5-08 — Background, foreground and rotation

- **Preconditions:** mission loaded; some selections made.
- **Procedure:** press Home and return; rotate the device if supported; observe state; repeat with a result screen if practical.
- **Expected:** no crash; behaviour is deterministic and documented. Selections may reset because the demo is stateless, but no false result, duplicate submission or persistence claim appears.
- **Evidence:** before/after screenshots, logcat, notes on whether state was preserved.
- **Pass/fail:** PASS if no crash or misleading state; a documented reset is acceptable. FAIL on crash, stale result presented as current or unintended submission.
- **Privacy/security:** do not inspect the recent-apps screen of other applications; return directly to CYBERQUEST.

#### G5-09 — Restart after result

- **Preconditions:** result screen displayed.
- **Procedure:** force-stop the app; relaunch; observe.
- **Expected:** app returns to mission loading; the previous result is not restored; no saved progress, XP or competency appears.
- **Evidence:** relaunch screenshot, logcat, package state.
- **Pass/fail:** PASS if the result is not persisted and the app remains functional. FAIL on restored results, saved progress or XP.
- **Privacy/security:** none.

#### G5-10 — Repeated assessment interaction

- **Preconditions:** result screen displayed.
- **Procedure:** use Try again; complete a second assessment; repeat once more; observe selections, results and network calls.
- **Expected:** Try again clears the previous result and selections; each assessment is an independent POST; results are not accumulated; no crash or duplicate submission.
- **Evidence:** screenshots after each cycle, gateway POST count, logcat.
- **Pass/fail:** PASS if repeated cycles are independent and deterministic. FAIL on accumulated state, duplicate POSTs or crash.
- **Privacy/security:** none.

#### G5-11 — Local data handling and cleanup

- **Preconditions:** app used through at least G5-03 and G5-10.
- **Procedure:** inspect only the app's private sandbox (`adb shell run-as com.cyberquest.app` file listing); check for databases, shared preferences, files and caches; uninstall the app; verify package removal and absence of app data.
- **Expected:** no account, token, learner profile or result history is stored; only transient runtime state exists, if any; uninstall removes the package and its data; `allowBackup=false` remains effective.
- **Evidence:** sandbox listing (file names only), package list before/after, uninstall output.
- **Pass/fail:** PASS if no persistent learner/personal data is found and uninstall is clean. FAIL on tokens, account data, retained results or residual app data.
- **Privacy/security:** inspect only `com.cyberquest.app`; never inspect `/sdcard`, other apps, contacts, messages, photos or accounts.

#### G5-12 — Cold offline start and reconnection

- **Preconditions:** app not running; networking disabled; no cached mission available.
- **Procedure:** launch the app offline; observe; restore networking; tap Retry.
- **Expected:** useful error with Retry, no crash, no fabricated or cached mission; after restoration, the mission loads from the server.
- **Evidence:** offline/error and recovered screenshots, logcat, API/gateway logs.
- **Pass/fail:** PASS if offline start fails usefully and recovery is explicit. FAIL on crash, blank screen without guidance, stale content or false success.
- **Privacy/security:** none.

#### G5-13 — Layout, readability and accessibility observations

- **Preconditions:** mission and result screens available.
- **Procedure:** inspect at default font and display size; repeat at a larger font/display size; portrait and landscape if supported; traverse with TalkBack or the accessibility scanner if available; check touch targets, contrast, clipping and reading order.
- **Expected:** core content and controls remain reachable and operable; no critical clipping; status is not conveyed by colour alone; controls have usable labels/roles. Non-critical cosmetic issues are recorded, not hidden.
- **Evidence:** screenshots at each setting, notes on TalkBack announcements and any unreachable controls.
- **Pass/fail:** PASS if all core content is reachable and all controls are operable; record non-critical issues for a separate fix. FAIL if a core flow is blocked or unreadable. No WCAG conformance claim is made.
- **Privacy/security:** do not capture notifications, other apps or personal content while changing system settings.

#### G5-14 — Server failure without false success

- **Preconditions:** mission loaded; endpoint controllable (API or gateway can be stopped or made to return 5xx/timeout).
- **Procedure:** make the assessment endpoint fail (stop upstream, return 5xx or force a timeout); submit; observe; restore; resubmit explicitly.
- **Expected:** a useful error, no result screen and no false success; no automatic retry; after restoration, an explicit submission succeeds.
- **Evidence:** error/result screenshots, gateway/API logs, logcat.
- **Pass/fail:** PASS if failures are honest and recovery is explicit. FAIL on a rendered result without a successful server response, silent failure or auto-retry.
- **Privacy/security:** use only the synthetic mission; no real targets or credentials.

#### G5-15 — Account/session isolation (not applicable)

- **Status:** **N/A — no accounts or sessions exist in this demo.**
- **Verification:** confirm there is no login, registration, profile, token, account switch or learner identifier in the UI or app sandbox. This is an absence check, not a security pass for future identity work.
- **Future trigger:** if identity, accounts or persisted learner data are introduced, this scenario must be replaced with real multi-user isolation, token lifecycle and data-separation tests. CQ-REQ-007 remains DESIGN_ONLY regardless of G5.

The Android client requires a trusted HTTPS endpoint; cleartext and self-signed fallbacks are correctly unavailable. Two options exist, each requiring separate authorization:

## 6. Evidence-capture and privacy procedure

### 6.1 Mandatory boundaries

- No inspection of personal applications, messages, photos, documents, contacts, call logs or accounts.
- No collection of personal data, device identifiers beyond the test device model/API, or account information.
- No `adb backup`, full `/sdcard` pull, contacts/SMS queries, or `dumpsys`/`content` queries against personal apps.
- No trust-all certificate configuration, no cleartext fallback, no production credentials, no real learner accounts.
- No real external phishing targets or live malicious content.
- Stop immediately if personal content appears.

### 6.2 Pre-run checks

1. Confirm DEV-01/DEV-02: reserved device or clean AVD, no personal accounts/data.
2. Record device metadata (DEV-03) and host tool versions.
3. Build the APK from the exact G5 commit with the authorized HTTPS endpoint; record SHA-256 and size.
4. Confirm the endpoint is trusted, HTTPS-only and reachable; confirm no tunnel/credential is left in the repository.
5. Enable Do Not Disturb; disable lock-screen notifications; close personal apps (without inspecting them).
6. Create a local evidence directory outside version control until review; use `docs/evidence/cq-00.7.2-g5/` only for approved synthetic evidence.

### 6.3 During the run

- Capture only the CYBERQUEST window. Prefer `adb exec-out screencap -p` over full-screen captures that include notifications.
- Filter logcat to the app PID: `adb logcat --pid=$(adb shell pidof com.cyberquest.app)`.
- UI dumps must be taken while CYBERQUEST is foreground; inspect only CYBERQUEST nodes.
- Record gateway/app outcome lines only: method, path, status, duration, outcome. No bodies, headers or client addresses.
- If a notification, message or personal content appears: **stop capture immediately**, do not read or record it, close the app if necessary, and document only that the stop procedure was triggered. Delete any accidental capture without inspecting it.

### 6.4 Evidence index and retention

For each scenario record: test ID, timestamp, device/APK identity, exact command, expected/actual result, screenshot/log filenames, SHA-256 of retained evidence, pass/fail and any defect ID. Retain only the minimum synthetic evidence needed for assessment. Delete raw dumps, temporary device files and unfiltered logs at teardown. Do not commit personal content, tunnel credentials or unrelated device data.

### 6.5 Teardown

- Uninstall `com.cyberquest.app`; verify package removal and app-data removal.
- Delete `/sdcard/cyberquest-*` temporary files created for testing.
- Stop the API, gateway and any authorized tunnel; verify the endpoint is unreachable and loopback ports are closed.
- Remove local temporary logs/captures not retained as evidence; record the teardown timestamp.
- Return the reserved device/emulator to its documented clean state.
