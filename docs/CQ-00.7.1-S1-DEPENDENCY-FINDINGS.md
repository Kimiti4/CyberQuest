## 2. Are the affected packages confined to development and documentation tooling?

Yes. The complete path from the repository manifest is:

```
web/package.json -> devDependencies -> @redocly/cli@1.34.5
                     -> @redocly/respect-core -> @faker-js/faker, js-yaml
                     -> @opentelemetry/{core,resources,sdk-*,exporter-*,propagator-*}
```

`@redocly/cli` is used by exactly one script, `npm run api:lint` (`redocly lint ../openapi/cyberquest-v1.json`), which validates the OpenAPI contract in CI and locally. It is not imported by application code, not referenced by the Next.js build, and not referenced by the Android client or the FastAPI service.

## 3. Does any of it enter a runtime or deployment artifact?

Verified, not assumed:

- **Production dependency tree:** `npm ls --omit=dev --all` contains **no** `@redocly/*`, `@faker-js/faker`, `js-yaml`, or vulnerable `@opentelemetry/*` packages. The only OpenTelemetry package in the production tree is `@opentelemetry/api@1.9.0`, pulled in by `next@16.4.1` itself; it is **not** among the flagged packages.
- **Built artifact:** a recursive scan of the production build output (`.next/`) found **no** reference to `redocly`, `@faker-js` or `js-yaml`.
- **Other artifacts:** the Android debug APK contains no JavaScript toolchain; the FastAPI service is Python-only. No Dockerfile or deployment manifest exists in the repository, so there is no container image carrying the dev tree.
- **CI:** the web job installs the full tree (including dev dependencies) to run lint, tests and the build. That is a build-time environment, not a runtime artifact.

Conclusion: the vulnerable packages do not ship in any runtime or deployment artifact that CYBERQUEST produces.

## 4. Accepted reason for not forcing an out-of-range upgrade

`npm audit fix --force` resolves the findings by installing `@redocly/cli@1.34.24`, which is **outside the declared dependency range** of the pinned `@redocly/cli@1.34.5`. Applying it would silently change a pinned dev-tool version as a side effect of a Next.js security upgrade, without compatibility review of that tool chain.

Decision: **not applied**. Rationale and boundary:

- The remaining risk is confined to a documentation/CI linting tool that processes a repository-local OpenAPI file. It is not internet-facing and not part of any shipped artifact.
- The pin exists for reproducibility (see `docs/DEPENDENCY-LOCKING.md`); bypassing it with `--force` would break the "reviewed dependency changes only" rule that the S1 checkpoint was created to uphold.
- Changing the lint tool version is a separate, reviewable change with its own CI signal, not a side effect of a security patch.

This is an **accepted residual risk with a recorded rationale**, not a silent waiver. If `@redocly/cli` is ever used against untrusted input, or its findings change severity, this decision must be revisited.

## 5. Next review trigger

Revisit this record when **any** of the following occurs:

1. `@redocly/cli` is upgraded, removed, or its dependency tree changes.
2. Any of the listed advisories receives a fix that changes the pinned version requirement.
3. The `@redocly/cli` lint step starts processing anything other than the repository-local OpenAPI file.
4. Any web runtime dependency begins to depend on a package in the flagged set.
5. A production deployment artifact is introduced (container image, bundle publish, or hosted deployment) that installs dev dependencies.
6. Next quarterly dependency review, or immediately before any production-readiness decision.
