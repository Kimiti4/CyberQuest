# CQ-00.6 — Security Verification Plan

**Status:** Planned test programme. None of the tests below is represented as executed by this document.

## 1. Verification rules

- A documented control is DESIGN ONLY until code/configuration exists.
- A unit test does not prove deployment configuration or end-to-end enforcement.
- Negative authorization tests must use at least two distinct learner identities and verify both read and mutation paths.
- Security tests use synthetic accounts/data and explicitly authorized test infrastructure.
- Any missing/ambiguous authorization decision is a denial, not a pass.
- Findings retain severity, reproduction evidence, affected commit, owner and retest result.

## 3. Minimum adversarial scenarios

1. Change a learner UUID in every resource route and query; no cross-learner data or mutation is permitted.
2. Submit client-supplied `xp`, `score`, `mastery`, `completed_at` and `entitlement`; server ignores or rejects them and derives all outcomes itself.
3. Replay the same event concurrently; at most one authoritative outcome/reward is created.
4. Reuse an idempotency key with a different request digest; return a conflict and create no side effect.
5. Submit an event for a stale mission version; do not reinterpret it against current content.
6. Logout or switch accounts with queued offline events; events must not cross account boundaries.
7. Attempt learner access to reviewer/admin operations; deny and audit without leaking privileged resource existence.
8. Inject HTML/script and external URLs into mission text; content is rendered safely and rejected where schema disallows.
9. Inspect application logs, CI logs and error responses for bearer tokens, passwords, recovery secrets, raw answer payloads and database connection strings.
10. Simulate identity/database unavailability; fail closed for protected operations and avoid leaking diagnostics.
11. Verify account deletion/export and retention across primary data, analytics processors and backup lifecycle.
12. Attempt to access private, loopback, link-local and cloud metadata endpoints from any future lab; all are blocked by external network policy.

## 4. Completion evidence format

Each test report records:
- checkpoint and requirement ID;
- repository commit SHA and environment;
- tool/runtime versions;
- test case and expected denial/success;
- actual result and relevant sanitized logs;
- severity and defect reference;
- reviewer and date;
- classification: PASS / PARTIAL / FAIL / BLOCKED / NOT RUN.

No test suite in this plan has been run as part of CQ-00.6.
