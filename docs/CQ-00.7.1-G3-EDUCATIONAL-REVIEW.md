# CQ-00.7.1-G3 — Educational Review

- **Checkpoint:** CQ-00.7.1-G3
- **Mission:** Phishing Detective — Suspicious Invoice (v1), fictional Nexus Corporation
- **Classification:** PASS, with one content defect found and corrected.
- **Reviewer basis:** assessment rubric, mission content, API feedback payload and rendered web result screen.

## Review criteria

1. Each warning indicator is technically accurate for the simulated message.
2. Neutral facts are not presented as malicious.
3. Feedback teaches why an indicator matters, not only that it was right or wrong.
4. Feedback supports safe verification and reporting behaviour.

## Indicator review

| Indicator | Type | Accuracy | Teaching value |
|---|---|---|---|
| `sender_domain` | Warning | Accurate: display name can claim any organisation; the domain is unverified | Explains checking the real sender domain against an official source |
| `reply_to_mismatch` | Warning | Accurate: replies follow the reply-to address, not the display name | Explains where replies actually go |
| `urgency_pressure` | Warning | Accurate: two-hour deadline with service-suspension threat | Explains urgency as a manipulation signal and advises slowing down |
| `unexpected_invoice` | Warning | Accurate: invoice was not expected; nothing verifies the debt | Explains independent verification against own records |
| `unverified_link` | Warning | Accurate: displayed link uses a non-organisational domain | Explains destination hiding and advises direct navigation |
| `invoice_reference` | Neutral | Correct: reference numbers are ordinary business detail | Explains why realism is not evidence of legitimacy |
| `team_greeting` | Neutral | Correct: generic team greetings are common and benign | Explains a greeting alone is not evidence of phishing |
| `business_hours` | Neutral | Correct: 09:14 arrival is ordinary | Explains arrival time carries no safety signal |

No indicator depends on guessing developer intent: every warning sign is evidenced by something visible in the simulated message (sender domain, reply-to domain, deadline pressure, unexpected invoice context, link domain).

## Defect found and corrected

**Defect:** Feedback returned only the indicator label as its `explanation`. The result screen therefore told a learner *what* was scored but not *why it matters* or *what to do* — insufficient for the educational acceptance criteria.

**Correction:**
- Added a `guidance` field to each indicator in `src/cyberquest/content/phishing_detective_v1.json`.
- The assessment API now returns `guidance` alongside `explanation` for every indicator.
- The web result screen renders guidance under each indicator status.
- `openapi/cyberquest-v1.json` declares `guidance` as required on mission indicators and on assessment feedback items, keeping the contract and runtime payloads aligned.
- Added regression tests: feedback guidance coverage, mission content guidance presence, and a web contract test for guidance rendering.

## Safe-response review

- Correct option: do not interact, verify through a known official channel, report through the approved process.
- Incorrect options (pay via link, reply to the sender, forward the link to a colleague) are each unsafe for stated reasons and receive corrective feedback.
- Correct-response feedback names verification and reporting; incorrect-response feedback still directs verification and reporting rather than only penalising.
